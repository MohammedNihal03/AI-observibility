# Scoring

## Read this first

The Observatory reports **observable agent behavior**. It does not report model internals.

| The Observatory says | It means                                                     | It does **not** mean                       |
| -------------------- | ------------------------------------------------------------ | ------------------------------------------ |
| Behavioral learning  | The agent's observable behavior improved during this session | Weights changed; gradients; loss went down |
| Agent health         | A weighted summary of measured behavior, 0–100               | Model quality, or a benchmark result       |
| Degradation          | Measured signals associated with the agent going in circles  | Proof that the model is failing            |
| Context pressure     | Token usage relative to a **configured** maximum             | A measured cause of degradation            |

Claude Code and Codex do not expose weights, gradients, backpropagation, loss, optimizer state or
learning rate to an external local application. Any product that claims to show you those for a
hosted coding agent is showing you something else. `ModelTrainingTelemetryProvider` exists in
`packages/collectors` for the day a local self-hosted model can supply real values; until then every
method returns `null` and the dashboard shows nothing.

## These thresholds are product decisions

The score bands below are **product design choices, not scientific measurements**. They were chosen
because they read clearly on a dashboard. They are not calibrated against any benchmark, and you
should retune them for your own workflow.

### Health states (Build.md section 26)

| Score  | State     |
| ------ | --------- |
| 80–100 | HEALTHY   |
| 60–79  | STABLE    |
| 40–59  | WARNING   |
| 0–39   | DEGRADING |

### Health weighting (section 25)

| Input                | Weight |
| -------------------- | ------ |
| Recovery             | 30%    |
| Tool efficiency      | 20%    |
| Repetition avoidance | 20%    |
| Goal adherence       | 15%    |
| Context management   | 15%    |

### Behavioral learning weighting (section 20)

| Input                       | Weight |
| --------------------------- | ------ |
| Recovery improvement        | 25%    |
| Error reduction             | 20%    |
| Repetition reduction        | 20%    |
| Goal adherence improvement  | 20%    |
| Tool efficiency improvement | 15%    |

### Degradation weighting (section 24)

| Signal                  | Weight |
| ----------------------- | ------ |
| Repeated failed actions | 30%    |
| Increasing errors       | 20%    |
| Recovery decline        | 20%    |
| Correction loops        | 15%    |
| Goal drift              | 10%    |
| Context pressure        | 5%     |

Every one of these numbers lives in a single configuration object in `packages/shared`. Change it
there and the whole system follows.

## Principles the scoring engine follows

**A failure is not a fault; failing the same way repeatedly is.**
One failed command followed by inspection, a fix and a passing retry is _healthy recovery_ and
should barely dent the score. The same command failing three times in a row is a strong degradation
signal. The engine distinguishes these by looking at what happened _after_ the failure, not just
that it happened (Build.md sections 16–18).

**Trends come from rolling windows, never from endpoints.**
Comparing the first event to the last event lets one unlucky moment define a session. Metrics are
compared across early / middle / recent windows instead (section 21).

**No classification without evidence.**
Below a minimum observation count the state is `INSUFFICIENT_DATA`. A session is never labelled
improving or degrading off the back of two events (section 22).

**Every score carries its reasons.**
A bare `Health = 62` is not an acceptable output. Each score returns a list of reasons derived from
the actual metric deltas that produced it. Reasons are never written by hand, never generated by an
LLM, and never invented when the numbers do not support them (section 27).

**Context usage is a signal, not a cause.**
High context utilization correlates with agents losing the thread. The Observatory reports the
correlation and refuses to claim the causation (section 23).

**Unknown stays unknown.**
No context maximum from the provider means no utilization percentage — the UI shows absolute usage
and says the maximum is unknown. No pricing for a model means `estimatedCost = null` and the UI says
"Cost unavailable". Neither is ever estimated into existence (sections 29–30).

**Determinism.**
Given the same events and the same configuration, the output is identical. No randomness, no clock
reads inside scoring, no network calls, no LLM (sections 50, 57).

## How each measured metric is defined

Precision matters more than brevity here: a counter whose definition is unclear is worse than no
counter, because it will be read as though it meant the obvious thing.

| Metric             | Definition                                                                                                                     |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| `totalToolCalls`   | Events that invoke a tool: `tool_call`, the three `file_*` types, `command_started`, `test_started`, `search`, `git_operation` |
| `successRate`      | Successful outcomes ÷ outcomes with a **reported** status                                                                      |
| `errorRate`        | Failed outcomes ÷ outcomes with a reported status                                                                              |
| `toolEfficiency`   | Successful `tool_result`s ÷ all `tool_result`s                                                                                 |
| `errors`           | Every event that failed — an `error` event, a failed command, a failed test                                                    |
| `filesRead`        | **Distinct paths** read, not read operations                                                                                   |
| `filesModified`    | **Distinct paths** written or edited                                                                                           |
| `commandsExecuted` | `command_started` events, plus `tool_call`s carrying a command string                                                          |
| `context.used`     | Peak of (input + cached) tokens on a single turn — a level, not a total                                                        |
| `durationMs`       | Span from earliest to latest event timestamp                                                                                   |

Three of these deserve their reasoning stated:

**Outcomes with no reported status are excluded from both sides of a rate**, not counted as
failures. An agent whose collector dropped a result did not fail — we simply do not know. Those
calls are reported separately as `unresolvedToolCalls` so the dashboard can distinguish "the agent
failed" from "the telemetry has a gap".

**Tool efficiency divides by tool results, not tool invocations.** Section 13 writes the formula as
`successfulToolCalls / totalToolCalls`, but its numerator is derived from results, so the
denominator must be the same population. Dividing results by invocations produced 75/49 on a real
session — over 1, clamped to a flattering 100%, while eight tool calls had in fact failed.

**Context is a level, not a running total.** Summing every turn's input tokens yields a number many
times larger than any real context window. The peak of (input + cached) on a single turn is what the
model was actually handed, and taking the peak rather than the last value keeps a mid-session
compaction from hiding that the window filled up. Output tokens are excluded: they are generated,
not occupying the input window.
